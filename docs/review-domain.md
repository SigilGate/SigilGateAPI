# Review: domain

## Краткий итог

Domain-слой в целом написан правильно — структуры понятны, пакет единый, Parse-функции работают. Есть одна логическая ошибка в `errors.go`, одна в `entities.go`, пропущены два типа в `types.go`, и небольшое расхождение в именовании.

---

## types.go

### Пропущены два типа

В спецификации определены семь типов. В `types.go` только пять — нет `PubId` и `AppealId`:

```go
// должно быть (по спецификации):
type PubId int         // ID пользователя в коммуникационном слое (Telegram pub_id)
type AppealId string   // UUID обращения в поддержку
```

Без них не получится реализовать `PublicUser` и `Appeal` позже.

### Расхождение в именовании аббревиатур

Ты используешь `UserID`, `DeviceUUID`, `NodeIP` — Go wiki рекомендует писать аббревиатуры целиком (`ID`, `UUID`, `IP`). Спецификация и эталонная реализация используют `UserId`, `DeviceUuid`, `NodeIp`.

Оба стиля встречаются в реальных Go-проектах. Важно выбрать один и придерживаться его везде. Поскольку маппер будет создавать ключи etcd из этих типов, а сервисы будут совместно использоваться — лучше придерживаться стиля спецификации (`UserId`, `DeviceUuid`, `NodeIp`).

## errors.go

### Главная проблема: `EtcdError` вместо `StorageError`

```go
// написано:
type EtcdError struct {
    Message string
}

// должно быть:
type StorageError struct {
    Cause error
}

func (e *StorageError) Unwrap() error {
    return e.Cause
}
```

Здесь три проблемы сразу:

**1. Нарушение принципа портов.** `EtcdError` — имя, которое знает о конкретной технологии (etcd). Domain-слой не должен знать, где хранятся данные — для этого и существуют порты. Если завтра вместо etcd будет PostgreSQL, придётся переименовывать тип во всём коде. `StorageError` — технологически нейтральное название.

**2. Потеря исходной ошибки.** `Message string` хранит текст, но не оригинальный `error`. Из-за этого нельзя использовать `errors.Is` и `errors.As` для поиска конкретного типа ошибки в цепочке:

```go
// С StorageError{Cause: err} — работает:
var storageErr *StorageError
if errors.As(err, &storageErr) {
    // исходную причину можно извлечь через storageErr.Unwrap()
}

// С EtcdError{Message: err.Error()} — цепочка оборвана,
// исходный error потерян навсегда.
```

**3. `Unwrap()` отсутствует.** Стандартный механизм раскрутки цепочки ошибок в Go требует метода `Unwrap() error`. Без него `errors.As` не сможет найти обёрнутую ошибку.

---

### `TokenExpiredError` и `TokenConsumedError` — хорошая идея, но рано

Оба типа логически правильные и понадобятся при реализации `JoinToken`-логики. Замечание одно: они тянут импорт `time` в `errors.go`. Лучше вынести их в отдельный файл или добавить вместе с `token`-сервисом — тогда станет понятен контекст.

---

### Формат сообщений: `%s` вместо `%q`

```go
// написано:
fmt.Sprintf("%s %s not found", e.Resource, e.ID)

// лучше:
fmt.Sprintf("%s %q not found", e.Resource, e.ID)
```

`%q` оборачивает строку в кавычки. Важно для отладки: если `e.ID` — пустая строка, `%s` напечатает `user  not found` (незаметно), а `%q` напечатает `user "" not found` (сразу видно проблему). То же касается `AlreadyExistsError`.

## entities.go

### Логическая ошибка: `APIToken.LastUsedAt time.Time`

```go
// написано:
type APIToken struct {
    ...
    LastUsedAt time.Time
}

// должно быть:
type APIToken struct {
    ...
    LastUsedAt *time.Time
}
```

`time.Time` имеет нулевое значение `0001-01-01 00:00:00 UTC`. Если токен никогда не использовался, отличить это от "использован первого января первого года" невозможно. `*time.Time` с `nil` явно выражает "никогда не использовался" — именно так это и хранится в спецификации.

---

### `JoinToken.ExpiredAt` → `ExpiresAt`

```go
// написано:
ExpiresAt time.Time  // ← спецификация

// у тебя:
ExpiredAt time.Time
```

`ExpiresAt` — "истекает в момент X" (будущее), `ExpiredAt` — "истёк в момент X" (прошедшее событие). Для поля, которое задаётся при создании токена, правильное название — `ExpiresAt`.

---

### Расхождение в именовании `APIToken`

Спецификация и эталонная реализация: `ApiToken`, `TokenId`, `CreatedAt`.
У тебя: `APIToken`, `TokenID`, `Created`.

Это следствие того же вопроса с аббревиатурами из `types.go`. Важно, чтобы имя типа (`ApiToken`) совпадало со стилем именования поля (`TokenId TokenId`) — всё в одном стиле.

---

### Смешанные отступы (tabs + spaces)

```go
type User struct {
    ID             UserID   // ← 4 пробела
	Status         Status   // ← таб
```

`gofmt` требует табы. Можно запустить `gofmt -w ./internal/domain/` — он исправит автоматически.
